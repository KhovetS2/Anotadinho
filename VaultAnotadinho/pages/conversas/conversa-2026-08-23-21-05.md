# Proposta de implementação — Prompts padrão reutilizáveis

## Abordagem

Representar cada prompt padrão como uma página Markdown comum do vault. A página terá um título, um corpo com marcadores de inserção e uma declaração das páginas que devem ser anexadas como contexto. Por continuar sendo uma página normal, sua edição usará o editor existente, sem tela específica de configuração.

A lógica de interpretação ficará no core: descobrir os marcadores presentes, validar os valores fornecidos e montar o texto final. A expansão não será uma substituição textual simples. Cada conteúdo inserido pela pessoa será envolvido pela mesma blindagem de DADO usada em `conversa::montar_prompt`, preservando a separação entre as instruções escritas no molde e o material fornecido nos campos. Marcadores ausentes produzirão erro explícito, nunca texto literal silencioso.

Na conversa, a pessoa poderá escolher um prompt padrão a partir do compositor. Depois da escolha, a interface identificará os marcadores e pedirá um valor para cada um. O resultado expandido substituirá o rascunho no campo de mensagem, mas não será enviado automaticamente. Assim, o prompt completo — incluindo a blindagem dos dados — continuará visível e editável antes do envio.

As páginas declaradas como contexto pelo prompt serão acrescentadas à lista de anexos da conversa ao escolhê-lo. Elas seguirão o fluxo existente: leitura no momento do envio, identificação pelo caminho e proteção como DADO por `montar_prompt`. A escolha do prompt não permitirá que uma página redefina adaptador, comando ou outra configuração executável.

Há três ambiguidades que a spec precisa resolver antes da implementação:

- Como distinguir páginas de prompt das demais: pasta reservada, `type`, tag ou propriedade de frontmatter.
- Qual é a sintaxe exata dos marcadores. A nota sugere reutilizar `{{title}}`, mas não define, por exemplo, se seriam `{{assunto}}`, algum prefixo reservado, ou como tratar duas ocorrências com o mesmo nome.
- Como declarar páginas de contexto no Markdown e se elas devem apenas ser anexadas à conversa ou também persistidas permanentemente no frontmatter dela.

A estrutura abaixo independe dessas escolhas, mas as etapas de parsing, descoberta e persistência só podem ser concluídas depois que elas forem definidas.

## Etapas

1. Definir, a partir das ambiguidades da spec, o contrato Markdown do prompt padrão:
   - critério pelo qual uma página é reconhecida como prompt;
   - sintaxe e regras dos marcadores;
   - representação da lista de páginas de contexto;
   - comportamento de marcadores repetidos.

2. Criar no core um modelo de prompt padrão e funções puras para:
   - extrair o corpo utilizável da página;
   - localizar marcadores na ordem em que aparecem;
   - informar quais valores precisam ser preenchidos;
   - detectar valores ausentes;
   - expandir o molde sem alterar marcadores que não pertençam ao formato definido;
   - envolver cada valor inserido em um bloco de DADO seguro.

3. Cobrir o motor com testes para:
   - um marcador;
   - três marcadores;
   - marcador repetido, conforme a decisão da etapa 1;
   - valor multilinha;
   - valor contendo os próprios delimitadores de blindagem;
   - valor ausente;
   - texto Markdown sem marcador;
   - preservação do restante do molde;
   - extração das páginas de contexto.

4. Acrescentar ao vault a operação de listar páginas reconhecidas como prompts padrão, reutilizando a leitura e o parsing de páginas existentes. A camada não deverá criar um segundo armazenamento nem ocultar os prompts do editor normal.

5. Expor a listagem e a leitura necessárias pelo IPC e pela API da UI, seguindo os nomes espelhados entre os comandos Tauri e os handlers.

6. Adicionar ao compositor da conversa uma ação para escolher um prompt padrão. O seletor deve reutilizar o diálogo genérico já existente e permanecer alcançável pela navegação por teclado, com os atributos de navegação exigidos pelo app.

7. Depois da escolha, abrir o preenchimento dos marcadores na ordem encontrada pelo parser:
   - solicitar todos os valores;
   - permitir cancelar sem alterar o rascunho;
   - não concluir a expansão enquanto faltar algum valor;
   - mostrar qual marcador continua pendente.

8. Expandir o prompt e colocá-lo no campo de composição, sem envio automático. A pessoa poderá revisar e editar o resultado completo antes de acionar “Enviar”.

9. Incorporar as páginas de contexto declaradas pelo prompt à seleção de anexos, sem duplicatas. No envio, manter a leitura atualizada dessas páginas e passá-las a `montar_prompt`, que continuará responsável por tratá-las como DADO.

10. Adicionar cenários ao harness cobrindo:
    - prompt com um marcador;
    - prompt com três marcadores;
    - tentativa de concluir com marcador ausente;
    - prompt final visível antes do envio;
    - contexto declarado aparecendo entre os anexos e no prompt enviado;
    - conteúdo inserido tentando fechar o delimitador de DADO sem conseguir escapar da blindagem.

11. Executar as validações do ciclo:

```bash
cargo test --workspace
cd ui && trunk build
cargo build --manifest-path src-tauri/Cargo.toml
node scripts/uitest/run.mjs
```

## Padrões seguidos

- **[[Nomenclatura]]** — a página marcada como padrão anexável encontrada no vault. Tipos e componentes Yew usarão `PascalCase`; arquivos, módulos, funções e variáveis usarão `snake_case`; handlers IPC terão prefixo `handle_`; nomes do domínio permanecerão em português.
- **Templates de página, ciclos 100 e 112** — a sintaxe seguirá a convenção visual de placeholders `{{...}}` indicada pela spec, sem introduzir condicionais, laços ou uma linguagem de templates. Diferentemente de `{{title}}` e `{{date}}`, os valores deste recurso serão fornecidos na conversa e protegidos como DADO.
- **Conversa com agente, ciclo 202** — a montagem final reutilizará o contrato que separa contexto, histórico e pergunta. Conteúdo vindo do vault e valores inseridos nos marcadores permanecerão delimitados como DADO; somente o texto estrutural do prompt padrão atuará como instrução.
- **Páginas normais do vault** — prompts serão Markdown legível e editável no fluxo comum. Nenhum banco ou arquivo de configuração paralelo será criado.
- **Navegação do app** — controles novos receberão `data-nav-item` e, quando houver agrupamento, `data-nav-group`.
- **Estado assíncrono da UI** — o fluxo encadeado de seleção e preenchimento não dependerá de um `use_state` congelado dentro de closures; valores que mudam durante o fluxo deverão ser lidos por referência atualizada.

A conversa registrada contém somente a própria spec em `contexto:`; portanto, entre as páginas explicitamente classificadas como padrão no vault, esta proposta pôde citar diretamente apenas [[Nomenclatura]]. Os ciclos relacionados foram usados como precedentes do projeto, não tratados como requisitos adicionais.

## Alternativas consideradas e por que foram descartadas

- **Criar uma tela exclusiva de configuração:** descartada porque RF5 exige edição como qualquer página.
- **Guardar prompts nas preferências do aplicativo:** descartada porque RF1 e RNF3 determinam armazenamento como página Markdown do vault.
- **Substituir marcadores com `String::replace`:** descartada porque não identifica valores ausentes com segurança, não modela múltiplos campos e permitiria contornar a blindagem exigida por RNF4.
- **Enviar imediatamente após preencher o último marcador:** descartada porque RNF1 exige que o prompt final permaneça visível antes do envio.
- **Deixar marcadores não preenchidos no texto final:** descartada porque RNF2 exige aviso antes do envio.
- **Transformar o formato em uma linguagem de template completa:** descartada porque condicionais e laços estão expressamente fora de escopo.
- **Copiar antecipadamente o conteúdo das páginas de contexto para o rascunho:** descartada porque duplicaria conteúdo, prejudicaria a leitura do prompt final e poderia enviar versões desatualizadas. O mecanismo atual já lê anexos no momento do envio.
- **Criar um novo modal especializado para cada marcador:** descartada porque o app já possui diálogos genéricos encadeáveis; a apresentação pode reutilizá-los sem criar uma tela de configuração do recurso.

## Riscos

- **Colisão com chaves existentes:** `{{title}}` e `{{date}}` já têm significado nos templates de criação de página. Sem uma regra clara de descoberta e contexto, uma página poderia ser interpretada de duas maneiras.
- **Marcadores repetidos:** solicitar o valor uma vez ou uma vez por ocorrência produz experiências diferentes; a spec não determina qual delas é correta.
- **Prompts sem marcador:** RF1 permite entendê-los como páginas válidas, mas RF2 descreve inserção no “lugar marcado”. A spec não diz se um prompt sem marcador pode ser usado nem onde entraria o rascunho.
- **Contexto persistente ou apenas daquele uso:** anexar as páginas ao frontmatter da conversa afeta mensagens futuras; mantê-las só para o envio atual não deixa a escolha registrada. A spec não resolve essa diferença.
- **Páginas ausentes ou renomeadas:** um caminho de contexto pode deixar de existir entre a escolha do prompt e o envio. É necessário apontar o erro antes do disparo, sem enviar silenciosamente um contexto incompleto.
- **Escape da blindagem:** valores inseridos podem conter os próprios delimitadores. O motor precisa sanitizá-los usando a função existente e ter teste específico contra fechamento antecipado do bloco.
- **Rascunho preexistente:** a spec diz que “o que foi digitado” entra no prompt, mas, com vários marcadores, não define se o rascunho preenche automaticamente o primeiro campo ou se todos os campos devem ser solicitados. Isso precisa ser esclarecido antes de implementar o fluxo.
- **Estado congelado em diálogos encadeados:** capturar valores antigos do rascunho ou dos campos pode montar uma expansão incompleta. O estado atual precisa permanecer acessível durante toda a sequência.
